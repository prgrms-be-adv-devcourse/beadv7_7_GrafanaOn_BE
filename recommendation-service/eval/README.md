# 추천 품질 평가 셋

유사 상품 추천이 좋아졌는지 **측정할 수 있게** 하려고 만든 정답 셋입니다.
Threshold 조정, 모델 교체, 필터 도입 같은 변경을 이걸로 검증합니다.

## 왜 필요한가

여태 상품 하나(2000001)의 결과를 눈으로 보고 판단했습니다. 그래서
Threshold 를 `0.45 → 0.40` 으로 내렸을 때도, 청킹을 실험했을 때도
**좋아졌는지 나빠졌는지 답할 수 없었습니다.**

정답 셋이 있으면 같은 질문에 숫자로 답할 수 있습니다.

## 파일

| 파일 | 용도 |
| --- | --- |
| `eval_label.csv` | **사람이 채우는 시트.** 100쌍, 순위·거리 숨김 |
| `eval_key.csv` | 정답키. 각 쌍의 현재 순위와 거리 |
| `score.sql` | 라벨을 넣고 지표를 계산 |

## 구성

기준 상품 10개 × 후보 10개 = 100쌍.

```
서사형 5개    story 150자 이상 — "첫 월급 타고 산 첫 드림슈즈..."
스펙형 5개    story 100자 미만 — "삼바 클래식 화이트 그린입니다..."
```

두 유형을 나눈 이유는 [rec_similar.md](../rec_similar.md) 에서 확인한 대로
**코퍼스가 서사형 40% / 스펙형 58% 로 갈려 있고, 둘의 거리 분포가 다르기** 때문입니다.
합쳐서 재면 어느 쪽이 문제인지 안 보입니다.

후보 10개는 이렇게 뽑았습니다.

| 구간 | 개수 | 목적 |
| --- | --- | --- |
| 현재 1~5위 | 5 | 정밀도 — 지금 내보내는 게 맞는가 |
| 15 / 30 / 60위 | 3 | 경계 — 어디서 잘라야 하는가 |
| 100위 밖 무작위 | 2 | 대조군 — 확실히 아닌 것 |

**상위만 넣으면 정밀도만 재고 놓친 것을 못 봅니다.** 그래서 중위·무작위를 섞었습니다.

## 라벨링 방법

`eval_label.csv` 를 Excel 로 열어 `적절1_부적절0` 열만 채웁니다. (UTF-8 BOM 이라 한글이 깨지지 않습니다.)

**순위와 거리는 일부러 빼고 후보 순서도 섞었습니다.** "1위" 라고 적혀 있으면
좋게 매기게 되어 평가가 무의미해집니다.

### 판정 기준

> **이 기준 상품을 보고 있는 사람에게, 이 후보를 같이 보여주면 납득할까?**

| 값 | 언제 |
| --- | --- |
| `1` | 납득함 — 같은 맥락·용도·취향. 이유를 한 줄로 설명할 수 있음 |
| `0` | 납득 안 됨 — 왜 이게 나왔는지 설명하기 어려움 |

애매하면 `0` 입니다. 추천은 **틀린 걸 보여주는 비용이 못 보여주는 비용보다 큽니다.**

판단이 갈린 쌍은 `메모` 에 이유를 적어두면 나중에 기준을 다듬을 때 쓰입니다.

### 참고 — 흔한 함정

* **같은 브랜드라서** `1` 을 주지 마세요. 브랜드 매칭이 목적이면 벡터가 필요 없습니다.
* **둘 다 스니커즈라서** `1` 을 주지 마세요. 217건이 거의 다 스니커즈입니다.
* 서사형끼리는 **이야기의 결**(첫 구매 / 이별 / 수집)이 겹치는지를 봅니다.
* 스펙형끼리는 **상품군과 상태**가 겹치는지를 봅니다.

## 채점

라벨을 다 채운 뒤:

```bash
# 1. 라벨을 DB 로 적재
docker exec -i commerce-postgres psql -U root -d dear \
  -c "DROP TABLE IF EXISTS recommendation.eval_label;
      CREATE TABLE recommendation.eval_label (pair_id TEXT PRIMARY KEY, label INT);"

# eval_label.csv 에서 pair_id 와 label 두 열만 뽑아 넣습니다
# (Excel 에서 두 열만 남겨 labels.csv 로 저장한 뒤)
docker exec -i commerce-postgres psql -U root -d dear \
  -c "\copy recommendation.eval_label FROM STDIN CSV HEADER" < labels.csv

# 2. 지표 계산
docker exec -i commerce-postgres psql -U root -d dear -f - < score.sql
```

`score.sql` 이 내는 것:

* **Precision@5** — 지금 상위 5개 중 몇 개가 적절한가 (유형별)
* **적절한 쌍의 거리 분포** — Threshold 를 어디에 둬야 하는지
* **순위 구간별 적중률** — 15위·30위·60위가 쓸만한지

## 이 셋으로 답할 수 있는 것

* Threshold `0.40` 이 맞나, `0.42` 나 `0.45` 가 나은가
* 서사형과 스펙型 중 어느 쪽이 더 망가져 있나
* 모델을 `text-embedding-3-small` 로 바꾸면 실제로 나아지나
* 서사 없는 글을 걸러내면 나머지 추천이 좋아지나

## 한계

100쌍 · 기준 상품 10개는 **방향을 보는 크기**이지 통계적으로 견고한 크기가 아닙니다.
Precision 차이가 5%p 안쪽이면 표본 오차와 구분되지 않습니다.
큰 결정을 내려야 하면 기준 상품을 30개로 늘리세요 — 같은 방식으로 재생성하면 됩니다.

라벨은 **한 사람이 매기면 그 사람의 취향**입니다. 가능하면 두 명이 따로 매기고
갈린 것만 합의하는 편이 낫습니다.
