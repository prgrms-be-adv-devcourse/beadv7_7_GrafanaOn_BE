# 최소 추천 기능 구현 문서

### 최소 추천 흐름
```text
Behavior Event
    ↓
UserInterest 계산
    ↓
상위 관심 Category 추출
    ↓
RecommendationItem Candidate 조회
    ↓
Basic Scoring
    ↓
Ranking
    ↓
Top-N Recommendation
```
### 1. 추천 행동 이벤트 모델 확장

사용자 행동을 추천 입력 신호와 추천 성과 측정에 활용할 수 있도록 행동 이벤트 구조를 확장했습니다.

| 이벤트 | 설명 | 관심도 계산 | 활용 |
| --- | --- | --- | --- |
| `IMPRESSION` | 추천 상품이 실제 화면에 노출된 경우 | 제외 | CTR 분모 |
| `CLICK` | 추천 영역에서 노출된 상품을 클릭한 경우 | 포함 | CTR 분자 |
| `VIEW` | 상품 상세 페이지 진입 | 포함 | 관심도 계산 |
| `SCRAP` | 상품 찜 | 포함 | 관심도 계산 |
| `CART_ADD` | 장바구니 추가 | 포함 | 관심도 계산 |
| `PURCHASE` | 구매 완료 | 포함 | 관심도 계산 |

- `eventId` 기반 중복 요청 방어
- 회원별 특정 기간의 행동 이벤트 조회 기능 추가
- `recommendationId`를 통해 추천 결과와 행동 이벤트를 연결할 수 있도록 구성

`CLICK`은 일반적인 상품 클릭이 아닌 **추천 영역에 노출된 상품을 클릭한 경우**를 의미합니다.

일반 상품 탐색에서 상품 상세 페이지에 진입한 경우에는 `VIEW` 이벤트로 기록하고있습니다.

---

### 2. 행동 가중치 정책 구현

사용자 행동마다 상품에 대한 관심 강도가 다르다고 가정하고 초기 가중치를 정의했습니다.

| 행동 | 가중치 |
| --- | ---: |
| `VIEW` | 1 |
| `CLICK` | 2 |
| `SCRAP` | 4 |
| `CART_ADD` | 5 |
| `PURCHASE` | 7 |
| `IMPRESSION` | 관심도 계산 제외 |

- 행동 이벤트에는 가중치를 저장하지 않고 실제 발생한 행동만 저장
- 행동별 가중치는 `BehaviorWeightPolicy`에서 관리
- 향후 가중치 실험 시 관심도 계산 로직의 변경을 최소화할 수 있도록 정책 분리

---

### 3. UserInterest 도메인 구성

`UserInterest`는 회원이 어떤 상품 카테고리에 얼마나 높은 관심을 가지고 있는지를 나타내는 상태 데이터로 사용하고있습니다.

```text
memberId=1 / SNEAKERS / score=16
memberId=1 / BOOTS    / score=4
```

관심도 계산 예시:

```text
SNEAKERS VIEW      → +1
SNEAKERS SCRAP     → +4
SNEAKERS CART_ADD  → +5

SNEAKERS 관심도 = 10
```

- 행동 유형별 가중치를 카테고리 단위로 합산
- 동일 `memberId + category`가 존재하면 신규 Row를 생성하지 않고 기존 관심도 갱신
- 마지막 관심도 계산 시각 관리

---

### 4. RecommendationItem Read Model 구성

`RecommendationItem`은 추천 서비스가 추천 후보를 생성하기 위해 사용하는 상품 Read Model로 사용하고있습니다.

Commerce의 `Product` 엔티티 및 Repository를 추천 서비스에서 직접 조회하지 않고, 추천에 필요한 최소 상품 데이터만 Recommendation 서비스 내부에서 관리하고있습니다.

현재 관리하는 정보:
- `productId`
- `category`
- `status`
- `viewCount`

두 도메인의 역할은 아래와 같이 이해해주시면 좋을것같습니다!

```text
UserInterest
= 사용자가 어떤 카테고리를 선호하는가?

RecommendationItem
= 현재 어떤 상품을 추천할 수 있는가?
```

추천 시 `UserInterest`에서 관심 카테고리를 추출하고, 해당 카테고리에 속하는 `RecommendationItem` 중 추천 가능한 상품을 Candidate로 조회하고있습니다.
~
현재는 Read Model 및 조회 구조는 구현되어있으나, Commerce의 상품 변경사항을 `RecommendationItem`에 전달하는 동기화 경로를 구현해야할것같습니다.!

수정될 예상 구조:

```text
Commerce Product
    ↓
Outbox
    ↓
Relay
    ↓
Recommendation Inbox
    ↓
RecommendationItem Upsert
```

### 5. 사용자 관심도 계산 서비스 구현

`UserInterestCalculationService`는 행동 이벤트를 기반으로 회원의 카테고리별 관심도를 계산하고있습니다.

처리 과정:

1. 회원의 특정 기간 행동 이벤트 조회
2. 관심도 계산 대상 행동 필터링
3. 행동 이벤트의 `productId`를 통해 상품 카테고리 조회
4. 카테고리별 행동 가중치 합산
5. `UserInterest` 생성 또는 갱신

```text
RecommendationBehaviorEvent
    ↓
BehaviorWeightPolicy
    ↓
ProductCategory 조회
    ↓
Category별 Grouping / Sum
    ↓
UserInterest
```
`IMPRESSION`은 사용자가 상품을 선택한 행동이 아니라 시스템이 상품을 노출한 사실이므로 관심도 계산에서 제외하고있습니다

---

### 6. 기본 추천 알고리즘 구현 과정
1. 회원의 `UserInterest`를 score 내림차순으로 조회
2. 상위 관심 카테고리 3개 선택
3. 해당 카테고리의 `ON_SALE` 상품을 Candidate로 조회
4. Candidate별 추천 점수 계산
5. 추천 점수 내림차순 정렬
6. 요청한 `limit`만큼 Top-N 추출
7. 최종 결과에 `rank` 부여
8. 추천 요청을 식별할 `recommendationId` 생성

현재 점수식:
```text
score = categoryInterestScore + log(1 + viewCount)
```
`viewCount`를 그대로 점수에 반영할 경우 인기 상품의 조회수가 추천 점수를 과도하게 반영될수있어  `log(1 + viewCount)` 를 점수식에 넣었습니다.
현재 점수식과 행동 가중치를 이후 테스트 결과를 기반으로 정규화 및 가중치 조정을 진행하고자합니다.
