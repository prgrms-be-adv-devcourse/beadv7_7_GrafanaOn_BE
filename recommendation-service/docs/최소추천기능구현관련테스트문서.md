
# 🧪 최소 추천 기능 구현 테스트 및 검증 계획
### 1. 행동 이벤트 멱등성 검증
#### 가설
> 동일한 행동 이벤트가 재전송되더라도 `eventId` 기반 멱등 처리를 통해 관심도 및 추천 지표가 중복 집계되지 않아야 한다.

#### 테스트
- 동일 `eventId` 순차 요청
- 동일 `eventId` 동시 요청
- DB Row 중복 여부 확인
- DB Unique Constraint를 통한 최종 중복 방어 확인
- `IMPRESSION`, `CLICK`의 `recommendationId` 검증

#### 목적
프론트 재시도 또는 네트워크 문제로 동일 이벤트가 여러 번 전달되더라도 추천 데이터가 왜곡되지 않는지 확인을 목적으로 두고있습니다.

### 2. 관심도 계산 정확성 검증
#### 가설
> 행동별 가중치를 카테고리 단위로 합산하면 행동 강도가 높은 카테고리가 더 높은 `UserInterest`를 가져야 한다.
#### 테스트 데이터
```text
SNEAKERS
VIEW × 3        = 3
SCRAP × 2       = 8
CART_ADD × 1    = 5
-------------------
Expected        = 16

BOOTS
VIEW × 2        = 2
IMPRESSION × 10 = 0
-------------------
Expected        = 2
```

#### 검증
- 기대 점수와 실제 `UserInterest.score` 비교
- `IMPRESSION` 관심도 제외 확인
- 기존 `UserInterest` 존재 시 INSERT가 아닌 UPDATE 확인
- 상품 정보가 존재하지 않는 이벤트 처리 확인
- 행동 데이터가 없는 경우 불필요한 조회 및 저장 여부 확인
---
### 3. 기본 추천 정확성 검증
#### 가설
> 관심도가 높은 카테고리의 판매 가능한 상품이 Candidate로 선택되고, 동일 카테고리에서는 상품 인기도가 Ranking에 반영되어야 한다.

#### 검증
- 관심도 상위 3개 카테고리를 Candidate Generation에 사용하는지 확인
- `ON_SALE` 상품만 Candidate에 포함되는지 확인
- `SOLD_OUT`, `DELETED` 상품 제외 확인
- 추천 score 내림차순 정렬 확인
- `limit` 적용 확인
- rank 순차 부여 확인
- 관심도 데이터가 없는 회원의 응답 확인
- Candidate가 없는 경우의 응답 확인
---

### 4. 행동 이벤트 증가에 따른 관심도 계산 성능 테스트
#### 가설
> `RecommendationBehaviorEvent` 데이터가 증가하면 회원별 기간 이벤트 조회가 `UserInterest` 계산 과정의 주요 병목이 될 가능성이 있다.

#### 데이터 규모
- 10K
- 100K
- 1M

#### 측정 지표
- Query Execution Time
- `EXPLAIN ANALYZE`
- Scan Row 수
- Index Scan 여부
- UserInterest 전체 계산 시간
#### 목적
인덱스를 선제적으로 추가하지 않고 실제 Query Pattern과 데이터 증가에 따른 병목을 확인한 후 적절한 인덱스를 선택하기위해 해당 테스트를 진행하려 합니다.

---
### 5. Candidate 증가에 따른 추천 성능 테스트
#### 가설
> Candidate 상품 수가 증가할수록 애플리케이션에서 수행하는 Scoring 및 Sorting 비용이 증가하여 추천 API 응답 시간이 증가할 것이다.
#### Candidate 규모
- 100
- 1K
- 10K
- 100K

#### 측정 지표
- Candidate DB 조회 시간
- Scoring 시간
- Sorting 시간
- 전체 추천 API 응답 시간
- p50 / p95 / p99
- RPS

병목이 확인되면 Candidate 사전 제한, DB 단계의 후보 제한, Popularity Score 사전 계산, Top-K, Cache 등의 방식을 비교할 예정입니다.

### 6. CTR 집계 성능 테스트
#### 가설
> 원본 행동 이벤트에서 매번 `IMPRESSION`, `CLICK`을 집계하는 방식은 이벤트 데이터 증가에 따라 CTR 계산 비용이 증가할 것이다.

**CTR 계산식** :

```text
CTR = CLICK / IMPRESSION
```
( 추천과 무관한 일반 상품 탐색 행동은 CTR에 포함 안함 )

#### 테스트
- 원본 BehaviorEvent 기반 CTR 집계 시간 측정
- 데이터 증가에 따른 집계 성능 변화 확인
- `recommendationId` 기반 집계 Query 실행 계획 확인
- `(recommendation_id, event_type)` 인덱스 적용 전후 비교
- 원본 집계와 사전 집계 방식의 성능 비교

병목이 확인되면 `RecommendationItemStat` 등의 사전 집계 모델 도입을 검토할 예정입니다.
